# 文档写作规范（插件 README + 论坛帖 + 设置文案）

> **读这文件的时机**：写/改任何插件 README、`forum-post-*.md`、或插件 yml 里的 `displayName` / `description` 时必读。改代码、发版、测试时不适用。
> 本规范从根 `AGENTS.md` 拆出，与 `AGENTS.md` 其他节无重复。

## 一、插件 README 编写规范

**精简基准**：以 studioToolsAuto / tagMergeAuto 的 README 为范例，只保留必要内容；交互类描述与逐步操作一律删除（参考 performerMerge v1.6.3 / tagMerge v2.4.3 精简）。

### 结构框架

插件 README 按以下顺序组织（无内容的章节省略）：

1. 头部 `> vX.Y.Z：` note（仅最新一条，见根 AGENTS.md 发版清单）
2. 定位段：1-2 句 — 做什么 + 核心机制一句话（纯 UI / 纯后台声明 + 数据语义）
3. 依赖
4. 安装（复制文件夹到插件目录 → 重启 → 入口出现即成功）
5. 设置（如有）
6. 触发方式表（入口 | 行为）
7. 核心机制（表/列表）：匹配规则 / 置信度规则 / 映射库格式 / 合并行为 / 应用效果（写入语义）
8. 文件说明（yml/js/css 表）
9. 注意事项

根 README.md：插件版本表（发版必同步）→ 安装（插件源 + 手动）→ 前置依赖表 → 触发方式表 → License；各插件详细说明只在各自 README。

### 内容取舍

**保留**：定位、依赖、安装、触发方式（入口→行为）、核心机制（匹配优先级 / 置信度规则 / 映射格式 / 合并行为 / 写入语义）、文件说明、注意事项；机制细节（分隔符、去重方式、字段合并规则、空值保护）属于 README 内容（见 ui-guidelines.md i18n 约定）。

**删除**：

- 交互类描述：按钮定义（忽略 / 应用全部 / 合并等）、折叠 / 收缩 / 展开等界面反馈、徽章位置与颜色、hover 提示、开关位置、状态行文案
- 逐步操作步骤（点击哪里 → 看到什么）
- 技术细节：JS 架构（幂等守卫 / i18n bridge / MutationObserver / DOM 注入）、CSS 约定、Python 内部实现
- 与上文重复的条目（触发方式表已覆盖的入口描述等）
- 「变更历史」整章（仅 sceneGallerySync 保留文末变更历史，见发版清单）

**篇幅**：能用表不用段落；一句话能说清的不写三句。

### 写完必做：逐句三问

README、yml 设置文案、论坛帖**同一标准**。逐句过，命中任意一问整句删掉或改写成结果：

| 问自己 | 命中的信号 |
|---|---|
| 这句在讲「怎么操作」还是「做什么」？ | 悬停多久、按几下、先点什么再点什么、拖到哪、手怎么放；重载后 / 刷新后 / 立即生效 / 不用重启 |
| 这句在描述界面本身？ | 按钮位置与颜色、开关叫什么、徽章、状态行、面板页签、页面变高变矮、先遮一下再撤 |
| 这句是我从实现里知道的？ | 类名、选择器、毫秒数、哈希、URL 规则、React / observer、运行时生成；格式规则（大小写、词数、字符集） |

判断不了就用这一条：**用户只看屏幕能不能得出这句话**。得不出就是实现细节，删。

### 例外：屏幕上找不到的入口必须写

快捷键（`Shift+Alt+B`）、修饰键（按住 `Shift`）、没有按钮可点的悬停/长按 —— 这些入口**界面上看不见**，不写用户永远发现不了，属于必须保留的内容，不算「操作描述」。

写**入口**，不写**过程**：「按住 Shift 整页露出」要写；「悬停 280ms 后」「先点一下再按住」「拖到卡片右下角」不写。判断法：这句话删了，用户还能不能找到这个功能？找不到就必须留。

反例（v0.1.7 设置项 `textStyle` 的 description 里混进去的）：

> sunny and letters are capitalised like Stash itself: every word in titles and names, only the first word in descriptions.

用户看到的就是一串小写词，不需要知道按句首还是按词首——整句删。「悬停片刻」删的是「片刻」，「改完立即生效」整句不进文档；但「悬停」「长按」「Shift」本身是入口，要按上一节留下。

## 二、论坛介绍文章（forum-post-*.md）

插件功能多次迭代后，Discourse 论坛帖内容可能滞后。更新论坛介绍时，在 `docs/` 下写 `forum-post-<插件名小写>.md`（如 `docs/forum-post-javstashlinker.md`），已被 `.gitignore` 排除、不随仓库发布，用户手动粘贴到论坛。

写作规则（极简优先，读者是论坛用户不是开发者；篇幅与详略以 `docs/forum-post-javstashlinker.md` / `docs/forum-post-performermerge.md` 为基准，超出即视为写复杂了）：

- **只写**：插件定位（解决什么问题）、各功能模块一句话职责、核心机制表（匹配优先级/置信度规则，每行一句话）、安装方式、依赖、配套插件；每个模块小节正文 ≤ 3 句（表格/条目另计）
- **Summary 表一句定位**：主操作 + 纯 UI 声明，不加机制枚举括号（证据分级链条等正文有表）、不加行为尾注（引用转移/源删除/仅追加）
- **禁举例**：规则直接写规则本身，名字/别名/变体/损坏串/大小写对比式的示例一律不写
- **禁入口总述与 UI 状态**：不写「图标打开面板有哪些标签页」入口总述（模块名由小节标题承载）、hover 提示内容、徽章数据清单、折叠/忽略的交互逻辑
- **禁字段级枚举**：合并/写入行为只留方向性一句（如「名字/图片始终保留目标」），不逐字段列规则（stash_id/URL/标签/收藏…），不写 append-only/空值保护细节
- **禁操作与提交细节**：逐条提交方式、失败跳过、批量跳过、完成后重扫时机均不写
- **禁后果推导与实现注脚**：规则后不追加「会导致什么」（匹配不到/漏报/误报来源等推导）；不写「与官方对话框同一 mutation」式说明、算法步骤链（分隔符→trim→去重）；模块定位性动机（Hi stashers 开场、模块首句问题引入）除外
- **兜底不写**：其余 UI 交互细节（按钮行为/折叠展开/开关位置/颜色尺寸）、底层实现（架构/i18n/observer/CSP）、功能开发逻辑——这些属于 README 的内容
- **注意事项归拢一处**：条目化，每条一句话，不展开「因为什么/会造成什么」
- 语言英文，保留原帖框架（Summary 表 + Hi stashers 开头 + 章节结构）与语气；只剩一层小节时总述标题（如「What it does」）可省；截图过时则移除占位，发帖时现截现传

## 三、插件 yml 的设置文案（displayName / description）

设置页上直接显示给用户，篇幅比 README 更紧。

| 字段 | 写法 |
|---|---|
| `displayName` | 英文名词短语，2–4 词（`Reveal text as well`）。是设置页左侧的名字，不是句子 |
| `description` | 一句话说「开了会怎样、关了会怎样」，只写结果；可选值用 `a = … ；b = …` 罗列；需要输入值的设置末尾加一句「Type one of those six names」这类约束 |

**不写**：操作过程（悬停多久、按几下、点哪个位置）、界面元素的位置与外观、格式规则（大小写、每项几个词、字符集）、实现（选择器、毫秒、哈希、运行时生成）、为什么这么设计。

**可以写**：入口本身——快捷键（`Shift+Alt+B`）、修饰键（按住 `Shift`）、没有按钮的悬停/长按；默认值；与其它设置的依赖（「Keep text readable 开着时本项无效」）。入口删了用户就找不到功能，按上一节算必须写。

改设置文案同样走上一节的「逐句三问」。
